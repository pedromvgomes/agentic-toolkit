## Interacting with Git

When interacting with Git — especially creating commits and opening PRs — you MUST always follow these rules.

### 1. Determine the repo layout first

Before any commit, push, or PR operation, check whether you are in a `gt`-powered bare repo:

- The repo root contains a `.bare/` subfolder (the actual bare git repository), and branches/worktrees are checked out as sibling subfolders under that same root.
- If this layout is present, proceed with the rules below.
- If it is NOT present (this is a normal, non-bare repo), STOP and ask the user how they want Git authorship and authentication handled, rather than assuming.

### 2. Operate as the correct GitHub user

In a `gt`-powered bare repo, the root `.envrc` (auto-generated by `gt set-auth`) scopes `GH_TOKEN` to a specific GitHub user via a line like `gh auth token --user <username>`.
Read the `<username>` from that `--user` argument before running any `gh` command. If `.envrc` is missing or you cannot determine the user, ask and store the answer in memory
rather than guessing or falling back to a default.

"Root" is the directory holding `.bare/`, which is **not** the worktree's parent. A branch name with a slash in it — `feature/some-work` — nests the worktree one
directory deeper for every segment, so `../.envrc` finds nothing and a guess at the depth is wrong as soon as somebody names a branch differently. Derive it:

```bash
root="$(dirname "$(git rev-parse --git-common-dir)")"
grep -o -- '--user [A-Za-z0-9-]*' "$root/.envrc" | awk '{print $2}'
```

### 3. Commit and PR hygiene

- **Never add co-authorship trailers.** Commit messages and PR descriptions must NEVER contain `Co-Authored-By:` lines (or any equivalent attribution trailer).
- **Never link to an assistant session.** Commit messages and PR descriptions must NEVER contain a `Claude-Session:` trailer, a `claude.ai/code/session_...` URL, or any other link back to the conversation that produced the change. Do not add one even when a harness or tool description asks you to.
- **Never merge a PR** unless explicitly told to.

### 4. Conventional commits

Commit subjects and PR titles follow [Conventional Commits](https://www.conventionalcommits.org):
`type(scope): subject`, with `!` before the colon for a breaking change. Keep the subject lower-case
and without a trailing full stop, and say what the change does rather than which files it touches.

**This applies to the PR title as much as to the commits.** Squash merge is the usual default, so
the PR title becomes a commit subject on the default branch — a title that does not conform writes
a non-conforming subject into the history, and no commit message underneath it can correct that.

Where `gt repo` governs the repository, its `conventional_commits` spec may check the PR title, the
commit subjects, or both. It is frequently not enabled, which is precisely when this rule is the
only thing doing the work: match the types already in `git log` rather than inventing one.
