## v0.14.0 — the entry manifest is its own type, and review depth follows the size of the change

`.agentic-toolkit.yaml` has been a `Stack` since the v2 stack model — `extends:`, per-category
lists, everything a `stacks/*.yaml` file can say. That made every entry-manifest-only fact
(where a repo's own definitions live, where its memory store is, which platforms to render) a
field bolted onto a type meant to be shared, guarded by a runtime check rather than by the type
system. This release gives the entry manifest its own type (ADR 0016), and, unrelated but
landing in the same cut, changes how much a review costs based on how large and how risky the
change actually is.

### Breaking: `.agentic-toolkit.yaml` is an entry manifest, not a stack

`extends:` is gone from the entry manifest. It is `stacks:` now, same shape, applied in the same
declared order:

```yaml
# .agentic-toolkit.yaml
root: agentic                # convention root for this repo's own content; default shown
context: ./CONTEXT.md        # optional, one file describing this repo to tooling

stacks:
  - github.com/owner/repo.git/stacks/default.yaml@ref
  - ./internal/team-stack.yaml
```

Per-category lists (`skills:`, `instructions:`, `rules:`, and the rest) are gone too — the entry
manifest no longer accepts a bare name or path under any of them. A repo's own definitions are
found by convention instead, under `<root>/<category>/` (`root` defaults to `agentic`), and win
over anything a composed stack contributes for the same name. A category directory that doesn't
exist is simply empty; two files under one directory declaring the same `name:` is refused,
because which one the consumer meant isn't knowable from the scan and dropping one silently
would render an incomplete repo.

`root:` and the new `context:` are native to the entry manifest's type. `context:` names one
file of free-form repo description, read verbatim and rendered as the first instruction in
`CLAUDE.md`/`AGENTS.md` — ahead of anything a stack names, which in turn sorts ahead of whatever
else this repo's own `instructions/` directory scans in, alphabetically by filename.

A `stacks/*.yaml` file you publish for others to import is unaffected: it's still a `Stack`,
still uses `extends:` and per-category lists exactly as before. Only the entry-point file's own
shape changes. See [MIGRATION.md](../MIGRATION.md#migrating-to-the-entry-manifest-split) for the
full before/after, including where to move definitions that were listed by name.

### Breaking: `platforms:` and `memory:` are repo properties

Both say something about the consumer — where to render, where the memory store lives — never
about a shareable stack. They are accepted only in `.agentic-toolkit.yaml` now; a `stacks/*.yaml`
file that sets either is refused with a `repo_only_field` error naming the field and pointing at
the entry manifest, rather than failing generically as an unknown field. Their shape in the entry
manifest itself is unchanged, so a consumer that already had them there needs no edit. One
consequence: `--source --stack <name>` renders a single named stack directly rather than a full
entry manifest, so a stack that used to set `platforms:` or `memory:` for that render path can no
longer do so — `--source --stack` now always targets Claude Code only.

### `agtk init` writes the new shape

The scaffold now seeds `stacks:` instead of `extends:` and points at convention scanning instead
of commented-out per-category keys, so what `init` writes parses under the entry manifest's
strict decoder without editing. `--extends` is renamed `--stacks` to match.

### New default instruction: `instructions-are-rendered-not-edited`

`stacks/default.yaml` now ships an instruction telling a consumer that `CLAUDE.md` and
`AGENTS.md` are rendered output: editing either file directly loses the edit on the next
`agtk render`, because render overwrites its managed region from the definitions and stacks it
was given, not from what a previous render left behind. To add an instruction, add a markdown
file under `<root>/instructions/` and render — no `agtk sync` needed unless a remote source also
needs refreshing.

### Breaking: review depth follows the size of the change, and a pull request follows the local rules

Every consumer without a code-review manifest of its own inherits this.

A risky signal (`auth`, `crypto`, `concurrency`, `sensitive-data`, `fix-revert`) used to raise a
local review straight to `deep` regardless of how much it touched, and could not raise a pull
request above `standard-codex` at all — the pull-request ceiling meant a large risky change on a
branch got read at full depth locally and at half of it in the PR. It now scales with
`changed_lines`, on both sides alike:

| changed lines | panel |
|---|---|
| under 20 | `focused` |
| 20–299 | `standard` |
| 300 and over | `deep` |

`focused` is new: one strong reviewer (`unified-extra`, opus) over all three axes, run twice for
agreement between independent instances — a small change carrying a risky signal gets a careful
single read rather than the specialist roster a `standard` or `deep` panel spins up for a change
with more surface to cover.

Pull requests carry the identical rules on the codex roster, and the pull-request default panel
changes with it: `defaults.pr` is `quick-codex` now, not `standard-codex`. A small pull request
that trips no escalation rule gets one codex reviewer where it previously got two. A pull request
with a risky signal and 300 or more changed lines now reaches `deep-codex`, which the old
`standard-codex` ceiling never let it reach — the size and signal rules raise or leave alone
exactly as they do locally, in both directions. `focused-codex` is `focused`'s codex twin.

This applies to the built-in default every repo without its own manifest uses, and to this
repo's own `.agentic-toolkit/code-review/manifest.yaml`, which carries the same change.

### Compatibility

- **Breaking — rename `extends:` to `stacks:` in `.agentic-toolkit.yaml`.** A per-category list
  in the entry manifest (`skills:`, `rules:`, etc.) no longer parses; move that content to files
  under `<root>/<category>/`. See [MIGRATION.md](../MIGRATION.md#migrating-to-the-entry-manifest-split).
- **Breaking — `platforms:` and `memory:` in a `stacks/*.yaml` file are refused.** Move either to
  your entry manifest if you had it in a stack you compose.
- **`agtk init --extends` is `agtk init --stacks`.** The scaffold it writes changed shape to
  match.
- **Breaking — a repo with no code-review manifest of its own spends differently.** Less on a
  small risky change (`focused` instead of `deep`) and less on a pull request with no escalation
  signal (`quick-codex` instead of `standard-codex`); more on a large risky pull request, which
  can now reach `deep-codex` where `standard-codex` used to cap it. A repo that wants the old
  behavior writes its own manifest (`agtk code-review init`) and edits the `changed_lines` rules
  or `defaults.pr`.
- **Action for existing consumers:** rename `extends:` to `stacks:` and move any per-category
  entries out of `.agentic-toolkit.yaml`, then `agtk update` (or re-run `install.sh`), `agtk
  lock`, and `agtk sync`. Consumers pinned to a tag also need to bump the ref to `@v0.14.0`.
