## v0.10.0 — the review skill sizes itself, and reviews PRs

A definition-only release on top of v0.9.0. No CLI or schema changes. `pre-pr-review` is replaced by two skills, and the default stack picks up a standing instruction about comments.

### New: `deep-code-review` — the reviewer fleet is sized to the change

`pre-pr-review` ran a fixed 2–3-agent panel per language bucket, whether the diff was a two-line config tweak or a rewrite of the auth filter chain. `deep-code-review` decides how much review the change deserves, and says so in one line before spending anything:

> Sizing: **medium** (14 files, 420 lines) · signals: **auth, migrations** · fan-in: elevated (JwtFilter → 11 files) → **rung 3, 6 agents**.

The ladder runs 0 → 3: a trivial diff with no risk signals is reviewed inline by the orchestrator with no subagents at all; a small clean change gets one agent; a medium one gets a 2–3 agent panel per language; a large or critical one gets up to 7. The user can override the rung at the single pre-flight gate.

Blast radius, not line count, drives the decision — a one-line middleware change outranks a 300-line rename. Three inputs combine: raw size, a list of twelve criticality signals (auth, DB migrations, shared kernel, public API contracts, message consumers, CI/CD, IaC, concurrency, PII/payment paths, crypto, feature flags, and a git-blame check for lines tracing back to a previous fix), and a *measured* reference fan-in for the changed exported symbols rather than a guess from the file path. Every threshold is documented in `references/sizing.md` and stated to the user as a heuristic.

### New: findings are independently validated before the user sees them

On rungs 2 and 3, every candidate finding is re-checked by a separate validator subagent whose only job is to decide whether the issue is real by rereading the code — opus for bug, security, and performance claims, sonnet for convention claims. Only `confirmed` and `downgraded` findings surface; rejections are reported as a count. Findings two reviewers converged on independently skip validation as already corroborated.

Every reviewer and validator also carries an explicit **do-not-flag list**: pre-existing issues on untouched lines, code that looks wrong but is correct, pedantic nitpicks, anything a linter would catch, issues silenced by a suppress annotation, and — unless the repo's own rules demand them — DoS, rate-limiting, and generic "validate this input" advice with no proven impact.

At rung 3 the review runs two *independent duplicates* of each core lane: two bug-hunters with split scopes and two conventions auditors, none told about the others. Convergence between them is measured at consolidation and treated as evidence. The 7-agent cap is per language panel, so a polyglot branch gets a full roster per stack; the sizing line announces the total across panels so the user can narrow the panels instead.

### New: `pr-code-review` — review a GitHub PR and choose what gets posted

A thin wrapper over `deep-code-review`. It resolves a PR by number, URL, or current branch, fetches it with `gh`, checks out the head code so reviewers get full-file context, and hands the diff to `deep-code-review` in pre-captured input mode.

The findings come back numbered, and **the user picks which ones become PR comments** — individually, by tier, or none. The default offers all RED plus high-confidence AMBER. Before anything is posted, the exact comment bodies are printed as a private dry-run and confirmed; selected findings then land as **one** `COMMENT` review with inline comments, deduped one per issue, anchored with full-SHA permalinks. Committable suggestion blocks are only used where applying one fully fixes the issue in under ~6 lines. The skill never approves and never merges.

### Reviewer prompts carry calibration, not a syllabus

The per-language prompts (`prompts/{go,rust,react,kotlin-spring,general}/`) hold what the reviewing model does not already know. Textbook taxonomies — OWASP lists, N+1 definitions, `useMemo` catalogs — are gone; so is every section the shared preamble already states. What remains is language-specific false-positive calibration ("before flagging a weak RNG, confirm the value is security-sensitive — `math/rand` for jitter is fine; for a token it is not"; "before flagging missing server timeouts, `Read` the middleware chain — these are configured once centrally") plus a short list of genuinely overlookable, version-stable traps. Across the 14 files that is 275 lines where the equivalent panel prompts ran 744.

### Repo rules are a first-class review axis

The conventions pass survives and is scoped properly: each convention doc governs only the files under its own subtree, `.agents/rules/**` and `.cursor/rules/**` are discovered alongside `AGENTS.md`/`CLAUDE.md`/`CONTRIBUTING.md`, and every convention finding must quote the exact rule and cite its source. The pass is now tiered by cost — skipped entirely when no docs exist, read inline by the orchestrator for a couple of short docs, and delegated to a haiku or sonnet extractor only when the docs are long. It no longer blocks behind its own approval round; the summary is shown at the single pre-flight gate.

### New instruction: comments describe the code, not its history

`comments-describe-code-not-its-history` joins the default stack. Comments state what the code does and why it is shaped that way, in the present tense — never which change produced them. No PR or ticket numbers, no "previously"/"used to"/"no longer", no "Regression:" preambles, no "Added"/"Moved from" bookkeeping. The failure mode a guard prevents stays in the comment; the changelog entry does not. ADRs are the one exception.

`deep-code-review` enforces the same rule as a review axis (`conventions:comment-hygiene`), so it is caught at review time as well as write time.

### Removed: the "Merge Commit Message" PR rule

The `git` instruction required every PR description to carry a "Merge Commit Message" section. It no longer does.

### Compatibility

- **No schema changes, no CLI changes.** The `agtk` binary is identical in behavior to v0.9.0; everything here is definition content.
- **Definition removal:** the `pre-pr-review` skill was removed in favor of `deep-code-review` (local reviews) and `pr-code-review` (GitHub PRs). `stacks/default.yaml` was updated accordingly, but any consumer that referenced `pre-pr-review` directly (by bare name or URL) must switch to `deep-code-review` and add `pr-code-review` for the PR flow.
- **Stack changes:** `stacks/default.yaml` gains the two new skills and the `comments-describe-code-not-its-history` instruction. The pre-approved script permissions in `skill-permissions` follow the scripts to their new path. Note what that pattern does and does not do: a leading `*` in a Bash permission rule spans anything, so `*/skills/deep-code-review/scripts/capture-diff.sh*` is satisfied by *any* path ending that way, including one inside a repo under review. The pre-approvals are a convenience, not a boundary — what keeps an untrusted PR from reaching them is `pr-code-review`'s untrusted-content rule and its detached review worktree, not the glob.
- **Action for existing consumers:** re-run `agtk lock` and then `agtk sync`. A plain `agtk sync` will not pick this up — the lockfile pins a SHA, and sync only re-locks when the lockfile is older than your config file. Consumers pinned to a tag also need to bump the ref in `.agentic-toolkit.yaml` to `@v0.10.0`.
