## v0.15.1 — the revert search stops giving up early, and a fallback that answers is complete

A patch release fixing three bugs that all made a review look worse than it was, or land worse
than it should: **`fix-revert` went undetermined on any diff of ordinary size, a fully-successful
provider fallback still posted as incomplete and stayed unapprovable, and `implement-handoff`
could close a handoff out from under a pull request that could not land.**

### `fix-revert` no longer gives up 25 hunks after the first routine commit

```
$ agtk code-review explain --json
agtk: escalate[0]: signal `fix-revert` could not be determined for this change: the search for
a revert stopped 25 hunks after the first routine repair (a signal that could not be read is not
a signal the change does not carry). Remove the rule, or narrow it with `touches`, rather than
leaving an escalation that can never fire
```

`detectFixRevert` traced a change's hunks back through git history looking for two things: a
routine `fix:` commit (`bugfix-lines`) and a revert or security repair (`fix-revert`). Once the
first class answered, the search for the second was capped to 25 more hunks instead of the full
200-hunk blame budget — a shortcut meant to save the subprocess cost of a search almost always
going to answer "no revert here" anyway. A `fix:` commit turns up within the first few hunks of
nearly any active repo, so in practice the shortcut fired on almost every diff past ~25-30
tracked hunks, and `fix-revert` read as undetermined on ordinary multi-commit branches — this
repo's own diffs among them, since `.agentic-toolkit/code-review/manifest.yaml` names `fix-revert`
in six escalate rules copied from the built-in default.

The shortcut is gone. The search for a revert now always spends the full blame budget,
independent of whether a routine repair already answered `bugfix-lines` — the two are
independent questions, and answering one first said nothing about how far the other needed to
look.

### A fallback that fully answers is a complete review, not a permanently blocked one

A panel retried on its declared `fallback:` after every run on it was blocked (an exhausted
provider quota, most often) posted a review that led with the blocked runs and "this review is
partial: what these would have found is unknown, not absent" — with no mention that a retry had
run at all, or that it answered cleanly. Worse, the posted marker that `reviewapprove` reads back
stayed `verdict=incomplete` even when the fallback fully answered, because completeness was
computed over every run ever made, blocked ones included, rather than over the panel that
actually reached a verdict. A pull request whose provider had a bad day stayed unapprovable for
as long as that provider did — silently, once the visible text stopped alarming over it.

Declaring a `fallback:` is the manifest saying the substitute panel is an acceptable answer when
the first is unavailable, the same way a panel's own quorum says one dissenting reviewer is an
acceptable substitute for unanimous agreement — so a fallback that fully answers is complete,
full stop. `Review.Superseded` splits what could not answer into the blocked runs a successful
fallback already covers (matched against which panel each run actually ran under, a new
`RunReport.Panel` field) and whatever is still genuinely missing; `Partial()` — and everything
built on it, `reviewMarker`'s `Complete`, the JSON `partial` field, and the review's own record
line all included — now reads only the second group. A run still unanswered on the fallback
panel's own attempt, or for an ordinary reason unrelated to a block, is still a real gap and
still blocks approval; nothing about that changed.

Whether a review fell back is now a separate question from whether it is complete, answered by
its own field rather than folded into the verdict: the posted body gets one line naming what it
replaced (`Retried here after every run on \`standard-codex\` was blocked; what follows is from
\`standard\`.`), and the JSON output's existing `fallback_from` field says the same thing
structurally. See ADR 0017.

### `implement-handoff` checks the pull request's own checks before closing the handoff out

Closing a handoff out (moving it to `handoff/done/`) happened immediately after `open-pr` posted
its review, with nothing in between that looked at whether the pull request could actually land.
A build already failing, a coverage gate already red, or a lint job already fired closed the
handoff out anyway, with no path back to it once that happened.

`implement-handoff` now reads `gh pr checks` before closing anything out. A check already
reported failing stops the run and leaves the handoff exactly where it was; a check still queued
or running is not a failure and does not block.

### Compatibility

- **No manifest, stack or CLI shape changes.**
- **A review posted for a panel that fell back renders differently and can approve differently.**
  The blocked runs it carries are unchanged; the wording distinguishing them from a genuine gap
  is new, and — the behavioral change — a pull request whose fallback fully answered is now
  approvable without a human override or the replaced provider recovering. Nothing about *when*
  a fallback is attempted changes.
- **Action for existing consumers:** `agtk update` (or re-run `install.sh`). `implement-handoff`
  is a skill under `stacks/default.yaml`; consumers of that stack also want `agtk sync` to pick up
  its new step.
