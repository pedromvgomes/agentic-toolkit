## v0.11.1 — curation runs

A patch release fixing one bug: **`agtk memory curate` could not complete a single run.** Every invocation died in the stream decoder, whichever job it was given:

```
$ agtk memory curate --dry-run
agtk: command failed
  → provider unavailable
  → json: cannot unmarshal string into Go struct field streamEvent.message
    of type struct { Content claudecode.messageContent "json:\"content\"" }
```

Both halves of the command were affected — the candidate backlog and the `--stale` sweep — so the one operation that writes to `notes/` had no working path. Every other memory command is deterministic and was unaffected.

### Cause

The fault is in `agentic-driver`, not here. Its Claude Code decoder unmarshalled each stream-json line into a struct that models `message` as an object, *before* reading the line's `type` to decide whether the line was one it cared about. Only three event types are ever read, so an event the package deliberately ignores — one whose `message` is a bare string — failed the whole run.

The failure was recorded as a known gap in v0.11.0 and attributed to compaction, on the reasoning that long runs compact and curation runs are long. That attribution was too narrow: a four-candidate `--dry-run` hits it too. The trigger is the event shape, not the run length.

### Fix

`agentic-driver` v0.4.0 → **v0.5.0**, which carries two changes:

- **An unmodelled line cannot fail the run, and an unreadable one is an event.** The decoder reads the type first and decodes the body only in the branches that use it — the same lazy treatment a tool result's `content` already had, applied one level up. A line that genuinely cannot be read is surfaced as an event rather than silently dropped, so a real decode failure in an event the package *does* read stays visible.
- **The codex provider reads its profile from a nominated `CODEX_HOME`**, matching the config-directory support the Claude Code provider already had.

No agtk source change was needed for either.

### Also in this release

- `.agentic-toolkit.lock.yaml` records `config_digest`, the field the resolver writes now that lockfile staleness compares content rather than mtimes. Committing it keeps the first `sync` on a fresh clone from re-locking, which is what fails offline.

### Compatibility

- **No schema changes, no CLI changes, no definition changes.** Behaviour is identical to v0.11.0 apart from curation completing.
- **The codex profile support is in the driver, not surfaced by agtk.** `agtk` constructs both providers from PATH with no configuration, so `CODEX_HOME` is honoured only as the codex CLI's own ambient environment. Nothing in `memory:` sets it.
- **Building from source still requires Go 1.26.6.**
- **Action for existing consumers:** `agtk update` (or re-run `install.sh`). No `lock` or `sync` is required — nothing a consumer renders has changed. Consumers pinned to a tag can bump the ref in `.agentic-toolkit.yaml` to `@v0.11.1`, but a v0.11.0 pin renders identical output.

### Known gaps

Unchanged from v0.11.0, except that curation can now clear them: this repo's own store carries staged candidates and stale notes that no run could previously promote or re-verify.

Which credential a curation run authenticates as still depends on the ambient environment. The driver passes the parent environment through untouched, deliberately, so the child CLI uses whatever the developer is already logged in with — but that means `CLAUDE_CONFIG_DIR` (or `CODEX_HOME`) being set or unset silently selects a different account, and a run launched from a different shell can fail to authenticate where an identical one succeeded. `agtk memory curate --check` resolves the provider, binary and grant without validating the session, so it reports a run as ready that authentication will then refuse.
