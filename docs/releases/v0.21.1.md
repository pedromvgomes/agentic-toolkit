## v0.21.1 — a backlog item records where it stands, and a release is the merge of its notes

### Breaking: a backlog item names its source, not its branch

A backlog item's body now carries a `Source:` line in place of its `Branch:` line: the first names the branch the work starts from, and the second named both the work branch and its base. The source is the branch the work starts from and the pull request targets. The body never names the branch the work happens on.

- **Items written before this release have a `Branch:` line and no `Source:` line.** `implement-backlog-item` stops on them with "the body names no branch to start from"; rewrite the body with `write-backlog-item`, and a person re-queues it after reading it.
- **`write-backlog-item` and `/plan-feature`** write `Source:` for every slice, stubs included.

### `implement-backlog-item` keeps its place in a progress comment

- **It chooses the work branch.** A fresh start derives `feat/backlog-<n>-<slug>` from the item's number and the verified body's Goal, and creates it from the source's head in a worktree of its own, without asking, unless the checkout already is at that head. It never moves the branch of the checkout it was started in.
- **The progress comment.** The branch, the source head and a table of tasks with their status and commits are kept in a comment marked `<!-- agtk:backlog-progress -->`. A restart takes the branch and what is done from it. The comment is read as state, never as work, and only from an author with write access; the branch it names must match the item's own pattern, and every commit it lists must be on the branch.
- **A changed body is detected.** The comment records the hash of the body the work was last reconciled with. A different verified hash rebuilds the task table against the new body, reviews the existing work against it, and stops for a person when it cannot tell what survives the edit.
- **Before the review**, the branch is rebased onto its source when the source has moved, and pushed with a lease pinned to the remote tip read beforehand. Every test suite the repository defines is run; release, publish, deploy and install targets are never run.
- **A mid-work save** posts the initial progress comment so that the next session resumes on the branch that holds the work.

### A release is the merge of its notes

A version is released when a pull request adding `docs/releases/vX.Y.Z.md` merges to `main`. `auto-release.yml` then tags the commit and publishes the release; the notes file becomes the body of the GitHub Release. Pushing a tag by hand no longer releases anything. See ADR 0030, and the `release` skill for the procedure.

This release is the first one cut this way.
