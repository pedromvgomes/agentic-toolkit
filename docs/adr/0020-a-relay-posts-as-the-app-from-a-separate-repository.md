# A relay posts as the App from a separate, registered repository

ADR 0019 draws the line between reading a pull request and posting to one, and closes with "posting on a machine that holds no registration is outside this decision." This decision is that case.

A machine with no App registration and no way to get one — a fresh container, a borrowed laptop, an agent session with a clean home directory — can read a pull request through the token fallback ADR 0019 describes, but `run --pr`'s posting path and `approve` still refuse outright: nothing on that machine can post as the App, and posting under anything else is the fallback ADR 0019 already rejected. `AGTK_CODE_REVIEW_RELAY=owner/name` names a second way out: a dedicated repository whose own GitHub Actions workflow holds an App registration of its own, and reruns `agtk` from scratch — `code-review run --pr N [--panel X]` or `code-review approve --pr N` — against a fresh checkout of the pull request, exactly as a registered laptop would. `relayOrRefuse` in `internal/cli/codereview_pr.go` dispatches that workflow and waits on it in place of refusing, and only in place of refusing: every path that reached a refusal before still reaches the same refusal first, and the relay only runs when that refusal is `githubapp.Unregistered` — never for a broken or half-written registration, which asks the operator to finish registering rather than being routed around, on this path exactly as on the read fallback's.

## Decision

**A relay posts as the App, through the App's own registration — not as anyone else.** The workflow the relay dispatches registers the App's raw credential (`agtk code-review register --key-stdin`, fed `AGTK_APP_ID`/`AGTK_APP_PRIVATE_KEY`) and then runs the same command a registered machine runs. Every review it posts and every approval it grants goes up through that installation, so every `ByViewer`-keyed invariant ADR 0019 describes — `LastReview` and `LastCompleteReview` skipping anything not `ByViewer`, `agtkThreads` keying a finding's thread only off a `ByViewer` root, suppression and folding acting only on a `ByViewer` fingerprint — holds exactly as it does on a registered laptop, because it is the same posting identity running somewhere else, not a new one. This is precisely why relaying is safe in a way ADR 0019's rejected "post as the token's owner" fallback was not: that option would have posted as whoever's token happened to be ambient, and every failure mode ADR 0019 lists — an approval `approve` cannot find, a review the next run pays for twice, a fingerprint marker the author's own comment can forge — follows from `ByViewer` being false or, worse, true for the wrong account. A relay never puts a token in that seat. The only credential that ever posts to the reviewed repository is the App's.

**The caller's own token never reaches the reviewed repository.** `relayOrRefuse` reads `GH_TOKEN`/`GITHUB_TOKEN` through the same `clientSeam.token()` the read fallback uses, and hands it to `relay.Dispatch`/`relay.Await` as `Target.Token`. Every call `internal/relay` makes with it is scoped to `Target.Slug` — the relay repository alone: triggering the relay's `workflow_dispatch` and reading its own Actions runs. Nothing in `internal/relay` ever names the repository under review as a request path; that repository's slug travels only inside the dispatch's `inputs`, as a string the relay's own workflow reads, never as a path this process's token calls against. So the boundary is not a policy this process chooses to honour — it is the only thing the caller's token is ever asked to do.

**Why a separate repository, and not this one or the one under review.** ADR 0012 places the App's key on a machine's own config directory specifically so its blast radius is one machine, and ADR 0009 is why that key is worth bounding this tightly: the installation token it mints carries `contents: write` on every repository the App is installed on, not merely permission to comment. Holding the raw key in `agentic-toolkit`'s own repository, or in whichever repository is presently under review, would put it exactly where ADR 0012's reasoning says not to: a repository other people's pull requests continually touch, with collaborators, forks and CI configuration churning under a key that mints write access everywhere the App is installed. A repository dedicated to nothing but this one workflow keeps the same one-holder property a registered machine already has — the key lives in exactly one place, accepted deliberately, not incidentally alongside unrelated traffic.

**This amends ADR 0012 again, narrowly — not a reversal of what it argued.** ADR 0012 rejects a shared runner for the coding-agent CLI's own credential: Codex's `auth.json` is rewritten in place on every session, its refresh tokens are effectively single-use once refreshed, and OpenAI's own guidance is not to share the file across concurrent jobs or machines — which forecloses a shared host running two GPT reviewers at once, and standing up such a host at all is a cost ADR 0012 rejects paying for a feature a laptop already runs for free. Both objections are about *that* repository being a general, standing service for arbitrary reviews. Neither is what this decision changes. The relay is not that: it is one repository dedicated to nothing but this one workflow, dispatched deliberately once per relayed post against a pull request already open, exactly the way ADR 0012 already lets a laptop run it. Whatever that workflow's own coding-agent credential needs when a relayed action runs a panel rather than only an approval is that repository's own concern to provision once, the same as any other machine's; this decision is about the App's own registration alone, which is not the credential ADR 0012's shared-runner objection was ever about.

**Two credentials, two jobs, kept apart the way ADR 0019 already keeps the App's key apart from everything else.** The relay's workflow uses a short-lived installation token from `actions/create-github-app-token`, scoped to the one repository under review, to check out that pull request at the git level — clone and fetch, nothing more. It uses the raw App id and key, fed to `agtk code-review register --key-stdin`, only for `agtk`'s own JWT-based calls to GitHub's API: the review it posts, the approval it grants. The first token cannot post a review or an approval that counts; the second is never asked to fetch a commit. This is the same line ADR 0019 draws between the App's own credential and every other kind of GitHub access this feature touches, applied here to the relay's own two calls instead of to a laptop's.

**`--force`, `--full` and `--json` refuse to relay, before anything is dispatched.** A relay is dispatched with only the pull request, the action and its panel (`relay.Request`'s `Repo`, `PR`, `Action`, `Panel`) — nothing that would tell the relay's own run to skip its no-op-on-an-already-reviewed-head check, or to read only the delta since the last verdict, or to answer with the review detail `--json` promises instead of a conclusion and a URL. Forwarding `--force` or `--full` unacknowledged would let the relay's own run apply its ordinary rules — no-op on an unchanged head, or a delta-only read — while this process still reported the dispatch a success, silently answering something other than what was asked. Forwarding under `--json` would hand a JSON consumer prose it cannot parse as the review it asked for. `runFlags.unforwarded()` and `relayOrRefuse`'s own checks refuse each one by name, before a relay run is ever started, and say to run registered or drop the flag. `--timeout` and `--max-parallel` are untouched because they bound a panel this process spends locally; a relayed run spends no panel here; the relay's own runner applies its own defaults, unaffected by either.

## Considered options

**Ship the caller's already-computed review through the dispatch payload, for the relay to post as-is.** A `workflow_dispatch` takes a small, fixed set of short string inputs, which is not a wire format a set of findings and a verdict fit into without inventing one, sized against a limit rather than against anything the review needs. It also has nothing to save: a relay reruns `agtk` from scratch against a fresh checkout, so nothing safety-relevant was computed locally in the first place to ship — dispatching a review this process already ran would require trusting a local run's output as much as a registered machine's own, which is exactly the case ADR 0019 already treats as needing the App's own posting, not a caller's say-so.

**Hand the App's raw private key to the ephemeral, unregistered machine itself.** This is ADR 0019's own rejected option for reads, reapplied: the key mints `contents: write` on every repository the App is installed on, and a container that holds it briefly to post is a container that held the widest credential this feature has, alongside a diff the operator did not write and a secret store that commonly delivers keys through the same environment a model inherits. The relay is what makes this unnecessary for posting too: the key never leaves the one dedicated repository it is registered on, and the unregistered machine holds only a token scoped to that repository's own Actions endpoint.

**Post under the caller's own token, from the relay repository, instead of running `agtk` there as the App.** Considered and set aside for the same three reasons ADR 0019 already gives for rejecting that fallback on a single machine: `approve` could never find a review posted that way, the next registered run would pay for a full panel again rather than reading on from it, and a fingerprint marker the pull request's own author typed would read as the App's. Moving the token to a second repository changes nothing about whose account it is — it is still not the App's installation, so `ByViewer` still answers false where the bookkeeping needs it true.

## Consequences

- Relaying costs a GitHub Actions run's own scheduling and startup time, on top of whatever the panel itself costs once it starts — `relay.DefaultTimeout` bounds the wait at twenty minutes for exactly this reason, wider than a registered machine's own panel would need.
- A relayed run is reported only as its conclusion and its run's URL. This process never reads the relay's own log, so it cannot show what was posted or why a run failed beyond GitHub's own conclusion string — what the relay posted is on the pull request itself, and its reasoning is in a log this process never opens.
- `--force`, `--full` and `--json` stay local-registration-only features. A relay that grows an input surface wide enough to carry any of them could lift this, but until then the refusal, not a silent difference in behaviour, is what a relayed run of any of them gets.
- `internal/relay` never imports `internal/githubapp` — a dependency the credential-surface guard now checks by name — so the package that carries a caller's token cannot reach the package that holds the App's key even by accident. Nothing about `githubapp.ReadClient`'s own guarantee (no write method, no exposed inner client) changes: the relay path never constructs a client from that package at all.
