# A relay posts as the App from a separate, registered repository

ADR 0019 draws the line between reading a pull request and posting to one, and closes with "posting on a machine that holds no registration is outside this decision." This decision is that case.

A machine with no App registration and no way to get one — a fresh container, a borrowed laptop, an agent session with a clean home directory — can read a pull request through the token fallback ADR 0019 describes, but `run --pr`'s posting path and `approve` still refuse outright: nothing on that machine can post as the App, and posting under anything else is the fallback ADR 0019 already rejected. `AGTK_CODE_REVIEW_RELAY=owner/name` names a second way out: a dedicated repository whose own GitHub Actions workflow holds an App registration of its own, and posts or approves through it in this machine's place.

`run --pr` and `approve` hand the relay different things, because they need different things from it. `approve` never runs a panel — it reads submitted reviews and comment threads and decides whether the head may be approved — so its relay is handed only the pull request and reruns `agtk code-review approve --pr N` from scratch, exactly as a registered laptop would. `run --pr`'s posting path does run a panel, and that panel runs on *this* machine: the pull request is read through the same token fallback `explain --pr` already uses, the panel runs here exactly as it would on a registered machine, and only the posting step — one GitHub review plus its file-level comments — is small and fixed enough to travel as a `workflow_dispatch` input. So the relay for `run --pr` is handed the review this machine already computed, as JSON, and its own run is `agtk code-review post`, which posts that review as the App and starts no model at all. `relayOrRefuse`/`resolveToPost` in `internal/cli/codereview_pr.go` dispatch the relay in place of refusing, and only in place of refusing: every path that reached a refusal before still reaches the same refusal first, and the relay only runs when that refusal is `githubapp.Unregistered` — never for a broken or half-written registration, which asks the operator to finish registering rather than being routed around, on this path exactly as on the read fallback's.

## Decision

**A relay posts as the App, through the App's own registration — not as anyone else.** The workflow the relay dispatches registers the App's raw credential (`agtk code-review register --key-stdin`, fed `AGTK_APP_ID`/`AGTK_APP_PRIVATE_KEY`) and then runs `agtk code-review approve --pr` or `agtk code-review post`, whichever the dispatch names. Every review it posts and every approval it grants goes up through that installation, so every `ByViewer`-keyed invariant ADR 0019 describes — `LastReview` and `LastCompleteReview` skipping anything not `ByViewer`, `agtkThreads` keying a finding's thread only off a `ByViewer` root, suppression and folding acting only on a `ByViewer` fingerprint — holds exactly as it does on a registered laptop, because it is the same posting identity running somewhere else, not a new one. This is precisely why relaying is safe in a way ADR 0019's rejected "post as the token's owner" fallback was not: that option would have posted as whoever's token happened to be ambient, and every failure mode ADR 0019 lists — an approval `approve` cannot find, a review the next run pays for twice, a fingerprint marker the author's own comment can forge — follows from `ByViewer` being false or, worse, true for the wrong account. A relay never puts a token in that seat. The only credential that ever posts to the reviewed repository is the App's.

**A `run --pr` relay is handed the review, not the pull request.** `agtk code-review post` reads one `relayedReview` — `reviewpost.Build`'s own `githubapp.ReviewPayload` plus its file-level comments — from standard input, checks it against the pull request's *current* head (refusing a review made against a head the branch has since moved past), refuses any event but `COMMENT` (approval is `code-review approve`'s alone), and posts it. Nothing about the panel, the diff, or the reviewed code ever reaches the relay: it receives exactly what a registered machine would have posted, computed by the caller, and its own job is only to be the identity that posts it.

**The caller's own token never reaches the reviewed repository.** `relayOrRefuse`/`routeToRelay` read `GH_TOKEN`/`GITHUB_TOKEN` through the same `clientSeam.token()` the read fallback uses, and hand it to `relay.Dispatch`/`relay.Await` as `Target.Token`. Every call `internal/relay` makes with it is scoped to `Target.Slug` — the relay repository alone: triggering the relay's `workflow_dispatch` and reading its own Actions runs. Nothing in `internal/relay` ever names the repository under review as a request path; that repository's slug, and for `run --pr` the computed review, travel only inside the dispatch's `inputs`, as strings the relay's own workflow reads, never as a path this process's token calls against. So the boundary is not a policy this process chooses to honour — it is the only thing the caller's token is ever asked to do.

**Why a separate repository, and not this one or the one under review.** ADR 0012 places the App's key on a machine's own config directory specifically so its blast radius is one machine, and ADR 0009 is why that key is worth bounding this tightly: the installation token it mints carries `contents: write` on every repository the App is installed on, not merely permission to comment. Holding the raw key in `agentic-toolkit`'s own repository, or in whichever repository is presently under review, would put it exactly where ADR 0012's reasoning says not to: a repository other people's pull requests continually touch, with collaborators, forks and CI configuration churning under a key that mints write access everywhere the App is installed. A repository dedicated to nothing but this one workflow keeps the same one-holder property a registered machine already has — the key lives in exactly one place, accepted deliberately, not incidentally alongside unrelated traffic.

**This amends ADR 0012 again, narrowly — not a reversal of what it argued.** ADR 0012 rejects a shared runner for the coding-agent CLI's own credential: Codex's `auth.json` is rewritten in place on every session, its refresh tokens are effectively single-use once refreshed, and OpenAI's own guidance is not to share the file across concurrent jobs or machines — which forecloses a shared host running two GPT reviewers at once, and standing up such a host at all is a cost ADR 0012 rejects paying for a feature a laptop already runs for free. Both objections are about *that* repository being a general, standing service for arbitrary reviews. Neither is what this decision changes, and the panel runs on the dispatching machine now more than it ever did under the design ADR 0012 first amended: `code-review post` and `code-review approve` start no model at all, so the relay repository needs no coding-agent credential of its own — this decision is about the App's own registration alone, which is not the credential ADR 0012's shared-runner objection was ever about.

**Two credentials, two jobs, kept apart the way ADR 0019 already keeps the App's key apart from everything else.** The relay's workflow uses a short-lived installation token from `actions/create-github-app-token`, scoped to the one repository under review, to check out that pull request at the git level — clone and fetch, nothing more. It uses the raw App id and key, fed to `agtk code-review register --key-stdin`, only for `agtk`'s own JWT-based calls to GitHub's API: the review it posts, the approval it grants. The first token cannot post a review or an approval that counts; the second is never asked to fetch a commit. This is the same line ADR 0019 draws between the App's own credential and every other kind of GitHub access this feature touches, applied here to the relay's own two calls instead of to a laptop's.

**`--force` and `--full` are accepted under a relay; `--json` is not.** The token fallback `run --pr` reads the pull request through always reports `ByViewer: false` (ADR 0019), so `chooseScope` and `carriesAVerdictFor` never find a review by this installation to vouch for, whatever either flag says: the path already reviews the pull request whole, on every relayed run, with or without `--force` or `--full`. Refusing them would ask an operator to drop a flag that changing nothing would have changed anyway. `--json` is different in kind rather than degree: a relayed run learns only how the relay's own run ended, which is not the review detail `--json` promises, so it is refused rather than handed a JSON consumer a line of prose. `--timeout` and `--max-parallel` are untouched because they bound the panel, which always runs on this machine now, relayed or not.

**Trusting a caller-computed review is a deliberate, accepted trade-off — not an oversight.** The "Considered options" section below is this decision's own record of the alternative: a relay that reruns the panel itself, trusting only the App's registration and never a caller's local output. That design was rejected in this repository's only relay repository, `pedromvgomes/agentic-toolkit-code-review-relay`, on the grounds that its runner would need its own coding-agent credential — the exact standing-service cost ADR 0012 already refuses to pay — for a review the caller has, by construction, already computed correctly on a machine that just ran it. The design this decision makes instead is narrower than "trust any registration": it trusts the caller's own review content, delivered to the App's registration through a dispatch only that caller's token can trigger. Whoever holds a token that can dispatch the relay workflow can make it post any review body under the App's real identity for the pull request's current head, including a body claiming a clean verdict with a forged `Review marker` — `code-review post`'s own check refuses a different event, a stale head, or a mismatched file-comment commit, but it does not, and cannot, verify that a body it is handed came from an actual panel run. This repository accepts that gap on one condition: the relay repository's own collaborator list is exactly the set of people whose pull requests it is trusted to post to. Under that condition, whoever could forge a review is also whoever the forged review would deceive, so the gap grants no capability a person did not already have by being able to open, approve, or merge their own pull request. The condition is load-bearing, not incidental: a relay repository opened to a second collaborator, a CI bot with its own write access, or any principal who is not also a trusted reviewer of the pull requests it posts to, changes what this trade-off is trading — it would then let one party forge what another party reads as the App's own verdict, which is exactly the failure ADR 0019 already rejects for a token posting directly. Widening the relay repository's collaborators is a decision to revisit this ADR, not a decision this ADR already covers.

## Considered options

**Have the relay's own workflow rerun `agtk code-review run --pr N [--panel X]` from scratch, dispatched with only the pull request and its panel, trusting nothing the caller computed.** This is the design that motivated separating the App's registration into its own repository in the first place, and it remains the more conservative trust model: the App's posting identity would then vouch only for a panel the App's own registered workflow ran. It was set aside because it requires the relay repository to hold a coding-agent credential of its own — an `agentic-driver`-compatible provider, its own auth, its own quota — standing and ready on every dispatch, which is exactly the shared-runner cost ADR 0012 already refuses to pay once (Codex's `auth.json` rewritten in place, effectively single-use refresh tokens, guidance against sharing the file across concurrent jobs). Provisioning and rotating that credential for a repository whose only job is to post reviews computed elsewhere would be paying that cost again for no reviewing this design does not already get from running the panel on the caller's own, already-credentialed machine. A repository that reruns the panel remains available as a stricter alternative should the trust trade-off above ever need tightening.

**Hand the App's raw private key to the ephemeral, unregistered machine itself.** This is ADR 0019's own rejected option for reads, reapplied: the key mints `contents: write` on every repository the App is installed on, and a container that holds it briefly to post is a container that held the widest credential this feature has, alongside a diff the operator did not write and a secret store that commonly delivers keys through the same environment a model inherits. The relay is what makes this unnecessary for posting too: the key never leaves the one dedicated repository it is registered on, and the unregistered machine holds only a token scoped to that repository's own Actions endpoint.

**Post under the caller's own token, from the relay repository, instead of running `agtk` there as the App.** Considered and set aside for the same three reasons ADR 0019 already gives for rejecting that fallback on a single machine: `approve` could never find a review posted that way, the next registered run would pay for a full panel again rather than reading on from it, and a fingerprint marker the pull request's own author typed would read as the App's. Moving the token to a second repository changes nothing about whose account it is — it is still not the App's installation, so `ByViewer` still answers false where the bookkeeping needs it true.

## Consequences

- Relaying costs a GitHub Actions run's own scheduling and startup time, on top of whatever the panel itself costs once it starts on the caller's own machine — `relay.DefaultTimeout` bounds the wait at twenty minutes for exactly this reason, wider than a registered machine's own posting step would need.
- A relayed run is reported only as its conclusion and its run's URL. This process never reads the relay's own log, so it cannot show what was posted or why a run failed beyond GitHub's own conclusion string — what the relay posted is on the pull request itself, and its reasoning is in a log this process never opens.
- `--json` stays a local-registration-only feature. A relay that grows an input surface wide enough to report structured review detail could lift this, but until then the refusal, not a silent difference in behaviour, is what a relayed run under it gets. `--force` and `--full` carry no such restriction: they are accepted because the relayed path already behaves as if both were always set.
- `internal/relay` never imports `internal/githubapp` — a dependency the credential-surface guard now checks by name — so the package that carries a caller's token cannot reach the package that holds the App's key even by accident. Nothing about `githubapp.ReadClient`'s own guarantee (no write method, no exposed inner client) changes: the relay path never constructs a client from that package at all.
- A relay repository's default branch must be named `main`. Dispatching by that name directly, rather than reading which branch is the default first, costs one request fewer on every dispatch, at the cost of this one required name — a relay repository whose default branch is called anything else has every dispatch refused with GitHub's own "no ref found" error.
- **Anyone who can dispatch the relay workflow can make it post any review body, under the App's real identity, for the pull request's current head.** This repository accepts that risk on the condition stated in the Decision above — the relay repository's collaborators are exactly the people whose pull requests it posts to — and treats a wider collaborator list on the relay repository as grounds to revisit this decision, not as a change this decision already anticipates.
